### 1.4 ทำไม Elysia + Bun แทน FastAPI

ฝั่ง Android ไม่ต่างกัน (Retrofit คุย JSON over HTTP) ความสามารถที่ต้องใช้ทำได้ใกล้เคียงกัน ตัวตัดสินคือทีมถนัด Elysia และมี `Bun.password`, `bun test`, WebSocket, `Intl.Segmenter` (ตัดคำไทย) ในตัว
**ความเสี่ยง:** ใบงานใช้ FastAPI → ถามอาจารย์ก่อน (ข้อ 3) ถ้าไม่ผ่าน schema ใน `DB_SCHEMA.md` และ API contract ใช้ต่อได้ทั้งหมด

| ชั้น | หน้าที่ | เทียบ FastAPI |
|---|---|---|
| Elysia | route, ตรวจรูปแบบข้อมูล, guard สิทธิ์ (JWT), รูปแบบ error, OpenAPI, CORS | FastAPI |
| Bun | รันโค้ด, ต่อ PostgreSQL, hash รหัสผ่าน, เทสต์, ตัดคำไทย | Python + uvicorn + SQLAlchemy |
| PostgreSQL | เก็บข้อมูล, ล็อกแถวกันจองซ้อน, ดัชนีค้นหา | PostgreSQL |

### 2.3 แค็ตตาล็อกและการค้นหา

หมวดอยู่ใน `migrations/002_seed_reference.sql` (78 แถว) · หมวดหนังสือเรียนจัดตามดิวอี้ 2 ชั้น (หมวดใหญ่ › หมวดย่อย) ใช้ 3 หลักเฉพาะ 004–006 เพราะคอมพิวเตอร์เป็นสาขาหลักของ สจล. ชื่อไทยทีมตั้งเอง ไม่คัดลอกตารางรายละเอียดของ OCLC (เลขดิวอี้ใช้จัดหมวดได้ แต่ตารางฉบับเต็มมีลิขสิทธิ์ ต้องตรวจเงื่อนไขก่อนส่งงาน)

| หมวดหลัก | หมวดย่อย |
|---|---|
| หนังสือเรียน | 000 คอมพิวเตอร์ (004 วิทยาการ · 005 โปรแกรมมิ่ง · 006 AI/มัลติมีเดีย) · 100 จิตวิทยา · 300 สังคม (เศรษฐศาสตร์ กฎหมาย การศึกษา) · 400 ภาษา · 500 วิทยาศาสตร์ (คณิต ฟิสิกส์ เคมี ชีววิทยา) · 600 เทคโนโลยี (แพทย์ วิศวกรรม เกษตร อาหาร ธุรกิจ) · 700 ศิลปะ (สถาปัตย์ ออกแบบ ดนตรี) · อื่น ๆ |
| อุปกรณ์คอมพิวเตอร์ | Apple Device · Notebook · PC Parts (รวมการ์ดจอ PSU เคส) · IT Accessories · มือถือและแท็บเล็ต Android · อื่น ๆ |
| เครื่องเขียน | ปากกา ดินสอไม้ ดินสอกด ไส้ดินสอ/ปากกา ยางลบ ลิควิด แม็ก สมุด กระดาษ วงเวียน ไม้บรรทัด ตลับเมตร กระเป๋าดินสอ อื่น ๆ |

- เล่มเดียวอยู่ 1 หมวดตามเนื้อหาหลัก **วิชาเป็นข้อความในรายละเอียด** (เล่มเดียวใช้หลายวิชา) ค้นด้วยรหัสวิชาได้
- ตัวกรอง: หมวด · ราคา · คณะ (หนังสือ) · แท็ก (แท็กกลาง + แท็กของหมวด 14 รายการ) · ไม่มีตัวกรองสภาพ/ยี่ห้อ/สเปก ใช้ช่องค้นหาแทน
- **ค้นหาภาษาไทย:** PostgreSQL ตัดคำไทยเองไม่ได้ → backend ตัดคำด้วย `Intl.Segmenter` (ทดสอบแล้วถูกต้อง) เก็บใน `listings.search_text` ใช้ full-text `simple` + `pg_trgm` เป็นตัวสำรอง (ค้นพิมพ์ไม่จบ) · ฟังก์ชันตัดคำใช้เหมือนกันตอนเก็บและตอนค้น ถ้าอัปเกรด Bun แล้วผลเปลี่ยนต้องรัน `bun reindex`
- **ทดสอบกับ PostgreSQL 17 จริงแล้ว (locale `en_US.utf8`):** ค้น "แคล" เจอ "แคลคูลัส", "โน้ตบุ๊ค เกม", "RTX 3060", "g102" ฯลฯ ผ่านทั้ง full-text และ trigram · `pg_trgm` กับอักษรไทยขึ้นกับ locale ถ้าสร้างฐานข้อมูลด้วย locale `C` ต้องทดสอบซ้ำ

### 2.6 ยืนยันตัวตน

**ตารางสิทธิ์**

| สถานะ | ทำได้ |
|---|---|
| ยังไม่เข้าสู่ระบบ | เข้าสู่ระบบ / สมัครคนนอก เท่านั้น (ไม่มี Guest) |
| มีบัญชีแต่ยังไม่ยืนยัน (คนนอก) | ดูสถานะ · ส่ง/ส่งบัตรใหม่ · ออกจากระบบ · ลบบัญชี |
| ยืนยันแล้ว (`is_verified`) | ทุกอย่าง (ผู้ดูแลเพิ่มเมนูผู้ดูแล) |

**KMITL SSO** (ตรวจจาก https://developer.kmitl.ac.th/blog/sso และไฟล์ discovery เมื่อ 2026-11-17)

- Keycloak OIDC · issuer `https://sso.kmitl.ac.th/realms/master` · สร้าง client เองได้ใน Developer Hub (แยก staging/production) · claim มาตรฐาน: `sub`, ชื่อ, `preferred_username`, อีเมล
- redirect URI ต้องเป็น `http(s)://` ห้าม wildcard ห้ามไอพีสาธารณะ → ตอนพัฒนาใช้ `http://localhost:3000/auth/kmitl/callback` คู่กับ `adb reverse`
- Student API: `GET https://api.kmitl.ac.th/student-catalog/v1/students/{id}` header `apikey` ให้ชื่อ คณะ สถานะ · **ใช้เฉพาะตรวจสถานะและคณะ ทิ้งชื่อกับรหัสนักศึกษาทันที**

1. แอปเปิด Custom Tab → `/auth/kmitl/start` (backend สร้าง state + nonce เก็บในหน่วยความจำ)
2. ผู้ใช้เข้าสู่ระบบที่ sso.kmitl.ac.th
3. สถาบันส่ง code กลับ `/auth/kmitl/callback` → backend แลก token (client secret อยู่ที่ server) ตรวจลายเซ็น id_token
4. เรียก Student API ตรวจสถานะ/คณะ → หา/สร้างบัญชีจาก `kmitl_sub` ตั้ง `is_verified`
5. เด้งกลับ `campusmarket://auth?code=` (ใช้ครั้งเดียว 60 วินาที หน่วยความจำ) → แอปแลกเป็น JWT

> **ต้องตรวจตอนล็อกอินจริงครั้งแรก:** SSO ให้ข้อมูลที่ใช้เรียก Student API ได้ครบไหม (`preferred_username` เป็นรหัสนักศึกษาหรือไม่) ถ้าไม่ต้องขอ claim เพิ่มจาก KDMC · API key ต้องรออนุมัติ 1–3 วันทำการ

**คนนอก:** สมัครด้วยอีเมล + รหัสผ่าน (hash `Bun.password` argon2id) + ชื่อที่แสดง ได้บัญชี `is_verified = false` ล็อกอินด้วยอีเมล + รหัสผ่านได้ทันทีแต่เห็นเฉพาะหน้าสถานะ แล้วยืนยันด้วยวิธีใดวิธีหนึ่ง (ไม่ยืนยันความเป็นเจ้าของอีเมล ไม่มีรีเซ็ตรหัสผ่านทางอีเมล ลืมรหัสให้ติดต่อผู้ดูแล)
- **ถ่ายบัตร:** อัปโหลดหน้าบัตร + เซลฟีถือบัตร ถ่ายจากกล้องเท่านั้น → คำขอ `PENDING` → ผู้ดูแลตรวจด้วยตา กรอกเลขบัตร ระบบแฮช (HMAC) กันซ้ำ → อนุมัติ (`is_verified = true`) หรือปฏิเสธพร้อมเหตุผล ไม่ใช้ระบบจดจำใบหน้า
- **ThaID (mockup):** หน้าจอและ `POST /auth/thaid/mock` เปิดเฉพาะโหมดพัฒนา ไม่ใช้โลโก้จริง การเชื่อมจริงต้องทำข้อตกลงกับกรมการปกครอง
- ทุกวิธีผ่านตัวกลาง `IdentityProvider` เดียวกัน สลับเป็นของจริงภายหลังได้

### 2.10 State Machine

**ประกาศ**

| สถานะ | ป้าย | ใครเปลี่ยนมา | ผลค้นหา |
|---|---|---|---|
| `AVAILABLE` | กำลังขาย | ผู้ขายลง/ลงใหม่/ส่งใหม่หลังตีกลับ · ระบบ (ยกเลิกการจอง) · ผู้ดูแลกู้คืน | ✓ |
| `RESERVED` | ถูกจอง | ระบบ เมื่อผู้ขายตกลงดีล | ✓ มีป้าย |
| `SOLD` | ขายแล้ว (Sold out) | ระบบ เมื่อผู้ซื้อกดได้รับแล้ว | ✗ |
| `CANCELLED` | ยกเลิกแล้ว | ผู้ขาย | ✗ |
| `RETURNED` | ถูกตีกลับ ต้องแก้ไข | ผู้ดูแล + เหตุผล | ✗ |
| `TAKEN_DOWN` | ถูกถอด | ผู้ดูแล + เหตุผล | ✗ |

ประกาศใหม่ขึ้นทันทีไม่ต้องรอตรวจ (ผู้ดูแลตีกลับ/ถอดทีหลังจากรายงาน) · ตีกลับใช้กับเรื่องที่ผู้ขายแก้ได้ ถอดใช้กับกรณีร้ายแรง

**ดีล**

```
PENDING ──ผู้ขายตกลง──▶ ACCEPTED ──ผู้ขาย "ส่งมอบแล้ว"──▶ HANDED_OVER ──ผู้ซื้อ "ได้รับแล้ว" หรือครบ 48 ชม.──▶ COMPLETED
   ├─ผู้ขายปฏิเสธ / มีคนอื่นถูกตกลง──▶ REJECTED
   └─ผู้ซื้อถอน / ประกาศถูกยกเลิก──▶ CANCELLED ◀── ACCEPTED (ฝ่ายใดยกเลิก → ประกาศกลับ AVAILABLE)
```

**ยืนยันตัวตนของคนนอก:** อัปโหลด → `PENDING` → ผู้ดูแลตรวจ → `APPROVED` (`is_verified = true`) / `REJECTED` (ส่งใหม่ได้)

### 2.13 ตัวชี้วัดความสำเร็จของผู้ขาย และการช่วยปิดดีลในระบบ

คำนวณตอน query ไม่มีคอลัมน์เพิ่ม:

| ตัวเลข | วิธีนับ |
|---|---|
| ปิดการขายสำเร็จ | ประกาศของผู้ขายที่ `SOLD` |
| **อัตราปิดการขาย** | `SOLD ÷ (SOLD + CANCELLED)` แสดงเมื่อปิดแล้ว ≥ 3 ประกาศ ไม่ถึงแสดง "ผู้ขายใหม่" |
| คะแนนรีวิว | เฉลี่ย โดยผู้ซื้อแต่ละคนนับครั้งเดียว |
| ยอดขาย (Dashboard) | ผลรวมราคาประกาศของประกาศที่ขายแล้ว (ค่าประมาณ ราคาต่อรองจริงอยู่นอกระบบ) |

**กันปั่นตัวเลข:** ขายแล้วเกิดจากดีลที่ผู้ซื้อยืนยันเท่านั้น · รีวิวเฉพาะผู้ซื้อของดีลสำเร็จ · 1 ตัวตน 1 บัญชี · ผู้ดูแลดูคู่ซื้อ–ขายซ้ำได้ตอนมีรายงาน · ช่องที่เหลือ: เพื่อนจริงช่วยกันปั่น (กันได้บางส่วนด้วยกฎผู้ซื้อคนเดียวนับครั้งเดียว)

**ทำให้ปิดดีลในระบบง่ายกว่า:** ปิดด้วยการกดการ์ดในแชต (ผู้ขาย 1 ครั้ง ผู้ซื้อ 1 ครั้ง หรือครบ 48 ชม.) · เตือนช่วยปิดดีล (ดีลตกลงแล้วเกิน 24 ชม. → แจ้งทั้งสองฝ่าย · ส่งมอบแล้วเกิน 24 ชม. → แจ้งผู้ซื้อ · สำเร็จแล้วชวนรีวิว และเตือนซ้ำหลัง 3 วัน) ส่งครั้งเดียวต่อดีลด้วย `NOT EXISTS` บนตาราง `notifications` · ประโยชน์เฉพาะดีลในระบบ: รีวิวและตัวเลขความน่าเชื่อถือ · ผู้ขายยกเลิกประกาศ ถามเหตุผล (ขายได้แล้วที่อื่น / เปลี่ยนใจ / ของเสีย) ไว้ดูว่ารั่วนอกระบบเท่าไร

### 2.14 ความปลอดภัยของข้อมูลและการเข้ารหัส

| ข้อมูล | วิธี |
|---|---|
| รหัสผ่านคนนอก | **hash** ด้วย `Bun.password` (argon2id) ถอดกลับไม่ได้แม้ฐานข้อมูลหลุด · คน สจล. ไม่มีรหัสผ่านในระบบเรา |
| ระหว่างทาง | HTTPS/WSS ตอนติดตั้งจริง · ตอนพัฒนาใช้ `http://localhost` ผ่าน `adb reverse` (ไม่ออกนอกเครื่อง) |
| Token | JWT อายุ 7 วัน เก็บในแอปแบบเข้ารหัส |
| รูปบัตร / เซลฟี | AES-256-GCM คีย์อยู่ใน `.env` แยกจากฐานข้อมูล เก็บใน `private/` |
| เลขบัตร | HMAC-SHA256 + secret ไม่เก็บเลขจริง |
| ข้อความแชต | เก็บแบบปกติ จำกัดสิทธิ์ด้วยโค้ด · เข้ารหัสที่ server เป็นส่วนเพิ่ม |
| End-to-end ในแชต | **ไม่ทำ** ยากและขัดกับระบบรายงาน (ผู้ดูแลจะอ่านข้อความหลอกลวงที่ถูกรายงานไม่ได้) |
